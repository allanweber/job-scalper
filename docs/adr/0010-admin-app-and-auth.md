# Admin web app, and the two authentication surfaces

Operators get a dedicated **admin web app**: server-rendered **FastAPI + Jinja2 + HTMX**
(same codebase, no separate JS build), run as its **own Dokploy service on a separate
subdomain** so it can be network-isolated and deployed independently of the public API.
Its capabilities are global settings / management config, user management
(list/search/suspend/delete + data deletion), plan/quota overrides, and job/queue + pool
monitoring. Runtime settings live in a Postgres **`settings` table, hot-applied**; every
state-changing action is written to an **`admin_audit`** table (who/what/when/before→after).

There are **two auth surfaces**:

- **Mobile / public API** — native Google Sign-In; the app posts the Google **ID token**,
  the backend verifies it and issues its **own access JWT + revocable refresh token** (DB).
  Stateless bearer auth, no cert pinning (TLS + JWT only).
- **Admin web app** — Google **web** OAuth redirect gated by an **admin-email allowlist**
  (env); a **server-side session cookie** (session store in Redis) keeps admins logged in.

## Considered options

- **Admin as a separate SPA (React/Vue)** — richer UX but a second build/deploy and its own
  auth handling for a tool a few admins use. Rejected for server-rendered HTMX.
- **Admin auto-generated by SQLAdmin/Starlette-Admin** — fast CRUD, but leans on SQLAlchemy
  models while the data layer is raw SQL. Rejected.
- **Admin mounted at `/admin` on the public API** — one deploy, but shares the public
  exposure surface and is harder to isolate. Rejected for a separate subdomain/service.
- **Separate admin username/password** — decoupled from Google, but a second secret store to
  build and secure. Rejected for Google + allowlist.
- **Admin session as a JWT-in-cookie or reused bearer JWT** — harder revocation for a
  privileged panel / JS-accessible token. Rejected for a revocable server-side session.

## Consequences

The codebase carries two auth mechanisms (stateless JWT for the API, cookie sessions for
admin) and multiple Google OAuth client IDs (Android, server/audience, web-admin). The admin
panel is a high-value target isolated on its own subdomain with an allowlist and audit trail.
Hot-applied settings mean operational tuning (cooldowns, quotas, default sources, feature
flags, maintenance mode) needs no redeploy; secrets remain in env, never the settings table.
